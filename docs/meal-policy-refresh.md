# 餐单策略升级与兼容规则（2026-10-25）

## 用户能看到什么

旧餐单打开时，APP 明确显示「饮食方案已升级」和「重新安排新版菜谱」。必须由本人或家人主动点击并确认；不能在更新 APP 或打开首页时自动消耗 API、更改饮食内容。已完成记录、原饮食日记、体重和吃饱反馈都保留。

点击后：
- 若当天还没有真实进食/没吃记录，新的 7 天菜单可以从今天开始。
- 当天已经打卡过任何一餐（包括 APP 餐单或独立饮食日记）时，新菜单从**明天**开始；不会把已吃的早餐替换成另一种早餐。
- 新菜单重新采用当前的渐进能量目标、忌口和完整营养约束，不继承上一版菜单、上一版目标热量或上一版 AI 的菜式建议。既有记录仅用于本地历史，不作为刷新请求的菜单模板。
- 系统仍保留以前各版餐单，用作追溯；新的覆盖未来日期优先展示。
- 无 API Key 时沿用本地验证过的食谱兜底，并如实说明来源；不能假装调用过 AI。

## 版本规则

`MealPlanPolicyRelease.current` 是**饮食策略发布版本**，不是应用的 UI 构建版本，也不等同于验证器 `PlanRules.version`。仅当能量策略、临床边界、核心规划提示词、食谱库、计量/排除逻辑发生可能改变菜单内容的重大变更时增加。纯 UI 修改不需要重建一周菜单。历史计划没有该字段时默认视为旧版本，允许一次主动升级。

每个新计划落盘 `planning_policy_version`。显式升级再记录 `policy_refresh_source_id`，阻止同源重复重建。新的窗口可能与旧窗口重叠（这是版本切换的刻意行为）；旧版记录不删，时间重叠时优先采用较新开始日期的新版计划。原有无升级标识的普通生成仍拒绝重叠日期。

## 不做的事

- 不强制依照老版本食谱和此前不合理的高频食材组合；不丢失实际吃过的客观事实。
- 不暗中降低热量、自动改写低盐约束或忽略医学筛查。
- 不在版本升级时重置长期体重目标和全部进度；新计划在现有个人档案和既有医学筛查基础上计算。
- 不声称这个产品版本号代表临床验证。

## 用户测试

更新后打开已有旧周 → 显示升级提示 → 先记录早餐 → 再升级 → 新周明天开始 → 重新进入饮食记录可见早餐 → 第二次尝试升级应拒绝；另测无记录时从今天开始、Hive 重启后无重复升级提示。
