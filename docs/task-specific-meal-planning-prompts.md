# AI 饮食规划分工：安全公共层 + 任务专属提示词（2026-10-25）

## 不按页面盲目增加 AI Agent
目前本 APP 的「菜谱规划」是一种结构化、受程序验证的生成任务；食物实际记录、食物营养计算、风险门禁、换餐规则等是**程序确定性逻辑**，不应该变成每点一次都让 AI 做临床决定。

一份生成请求依次由四段组成：
1. `clinicalSafetyPrompt`：所有任务共享，不允许诊断、调药、推断肾功能安全或突破营养约束。
2. `verifiedMenuSelectionPrompt`：只选入库完整食谱，兼顾主食、蛋白、蔬果、低盐、饱腹感与经济性。
3. `observedHistoryContinuityPrompt`：仅在常规下一周、初次规划和本周调整时使用，准确区分实际记录、未记录和计划建议；**重大策略重建明确省略这一块**，避免继承旧菜单。
4. `exactPlanJsonContractPrompt`：强制完整七天 JSON，程序独立计算并二次校验。

在这些共享规则之间再插入**互不混用**的五种任务提示词：
- `firstWeekTaskPrompt`：第一次做菜谱，更注重温和起步、三餐足量，不假设已有执行数据。
- `followingWeekTaskPrompt`：下一周，根据已观察吃饱反馈、实际记录和可持续性改进，但不自动加速减重。
- `remainingMealsTaskPrompt`：只修改剩余餐次，必须保留过去日期和已完成记录，热量合同不变。
- `policyRefreshTaskPrompt`：重大策略更新后的全新七天，严格不继承旧 AI 菜谱、旧热量目标或不实假设，既有实际饮食由本地保留。
- `validationRepairTaskPrompt`：营养、格式、日期、锁定项失败后的特定修复，不额外提出医学建议。

### 输入和输出
- 系统安全+任务提示词每次都重新发送；不是临时附加一个没有边界的自然语言备注。
- APP 仍然**只调用一次**规划接口（必要时最多按原有失败修复次数重试），不能拆成多个未经验证的自由 Agent，提高成本和一致性风险。
- 结构化数据通过 `input.mode` 明确路由，未知模式拒绝而非悄悄回退到首次减肥方案。
- DeepSeek 与兼容 API 保持同一 JSON 契约。文档更新不会更改 API key 安全存储方式或用户授权。
- 本地 `PlanRules.validate` 仍是可发布计划的最后一道营养校验。

### 与其他功能的边界
| 工作 | 执行位置 | 原因 |
| --- | --- | --- |
| 判断疾病风险、营养限值、低盐 | Flutter 代码 | 安全需要确定性 |
| 生成首次/下周/新版周餐单 | 大模型+任务提示 | 组合菜谱空间大 |
| 已记录过的餐次、换餐后剩余 | 专属限制提示 + 代码锁定 | 不能改写事实 |
| 直接交换一道本地已有菜 | 本地代码 | 无需额外 token |
| 四周回顾和饥饿阶段统计 | 本地代码 | 未记录不能推断 |
| 下一周基于回顾选菜 | 下周任务提示 | 仅参考证实的记录 |
| 失败校验再次重写 | 修复提示 + 本地验证 | 不得猜营养 |

本次 PR 主要是拆分提示词的**职责、路由和测试**，不是声称 AI 有新的专业医学能力，也不改变当前阶段热量的确定性数值。改变这些阶段算法须单独审查并升级餐单策略版本（见另一个 PR）。
